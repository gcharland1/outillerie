## Réponses de l'utilisateur

- **Q1 (2026-11-21)** : SMTP générique par `smtplib`, configuré par variables d'environnement. L'utilisateur choisit le fournisseur, règle SPF/DKIM et remplit le `.env` du serveur avant le merge. La livraison ne pose pas de question : l'utilisateur le confirme avec son accord sur la spec (étape 8).
- **Q6 (2026-11-21)** : bloquer les nouveaux engagements, demander un emprunt (`loans.new`, `loans.create`) et accepter une demande (`loans.act` accept). Restent permis : refuser, le suivi des prêts en cours, les outils et les contacts.
- **Q5 (2026-11-21)** : `email_confirmed_at timestamptz NULL` ; les comptes existants restent non confirmés (pastille, bandeau, renvoi depuis le profil avant d'emprunter ou d'accepter) ; aucun envoi groupé au déploiement.
- **Q13 (2026-11-21)** : le lien (GET) affiche une page dont le bouton « Confirmer mon courriel » envoie le jeton par POST (contre les scanners de liens) ; un filtre de journalisation masque le jeton dans les lignes de requête de Werkzeug ; le jeton reste possible dans les journaux de Cloudflare Tunnel, risque accepté et noté dans l'ADR. (Une première version de la question affirmait à tort que le POST seul gardait le jeton hors des journaux ; corrigée avant la réponse.)
- **Q16 (2026-11-21)** : squat d'adresse accepté comme limite (design et ADR) ; issue de suivi « libérer l'adresse d'un compte jamais confirmé » à ouvrir après accord de l'utilisateur sur son texte.
- **Q9 (2026-11-21)** : au plus un envoi toutes les 5 minutes par compte, mesuré par `email_confirmation_sent_at` (posé à chaque envoi, inscription comprise) ; pendant le délai, message neutre avec le temps restant.
